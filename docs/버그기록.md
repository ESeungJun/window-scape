# 버그 기록

## 2026-11-13 큰 창에서 렉과 발열(미니어처)

- 증상: 16인치 인텔 맥(Radeon Pro 5300M)에서 미니어처 모양을 띄우고 창을 크게 키우면 끊기고 노트북이 뜨거워졌다.
- 재현: 크롬 1728×1080 창(레티나 2배), 해안도로·낮·맑음. `EXT_disjoint_timer_query_webgl2`로 `renderer.render` 한 번의 GPU 시간을 쟀다.
- 원인
  1. 픽셀 비율이 창 크기와 상관없이 화질 '높음'이면 2였다. 큰 창은 그리기 버퍼가 약 580만 픽셀이 되고 GPU 시간이 픽셀 수에 거의 비례한다(비율 2: 17ms, 1.5: 10.6ms, 1: 4.4ms). 위젯처럼 작은 창만 생각한 설정이라 그동안은 드러나지 않았다.
  2. 새로 넣은 미니어처 배경(`backdrop.ts`)을 깊이 검사 없이 맨 먼저 그려, 판에 가려질 픽셀까지 모두 계산했다(큰 창에서 +3ms).
- 수정
  1. 화질마다 한 프레임에 그리는 픽셀 수에 상한을 뒀다(`pace.ts`의 `PIXEL_BUDGET`·`pixelRatioFor`, 높음 300만·보통 200만·낮음 100만). 창이 크면 비율을 낮추고, 1 아래로는 내리지 않는다.
  2. 배경은 불투명한 것 중 맨 마지막에 깊이 검사를 켜고 그린다.
- 전후(같은 창, GPU 시간 중앙값): 미니어처 17.6ms → 5.7~9.2ms, 디오라마 12.4ms → 6.8ms. 배경만 보면 비율 2에서 3ms → 2.2ms.
- 앱 기준 재측정(사용자 요청): 데스크톱 앱은 `low-power`라 **내장 인텔 GPU**로 투명 창을 그린다. 크롬(외장 GPU)과 병목이 달라서, 위 두 수정만으로는 앱에서 내장 GPU 63% → 53~66%(측정 흔들림 큼)로 거의 줄지 않았다. 앱 큰 창(1728×1080, 미니어처)에서 하나씩 꺼 보니 픽셀 비율 1은 48%, 초당 20번은 31~44%, 초당 15번은 35%, 기존 '절전' 설정은 23%였다. 프레임마다 드는 고정 비용(투명 창 합성, GPU 간 복사로 보임)이 커서 **덜 자주 그리는 것**이 가장 잘 듣는다.
- 추가 수정: 데스크톱 앱은 창이 900×650(CSS 픽셀 넓이)보다 크면 저절로 절전처럼 그린다(`pace.ts`의 `lowPowerFor`, 조작 중 30번·가만히 있으면 15번, 화질 한 단계 아래). 기본 위젯(440×320)과 웹은 그대로다. 앱 큰 창 결과: 내장 GPU 56~67% → 24%, 앱·WebKit CPU 합 30~32% → 11.5%(20초 평균 두 번).
- 측정 방법(앱): `ioreg -c IOAccelerator`의 Device Utilization %와 `ps`의 window-scape·WebKit 프로세스 CPU%를 1초마다 20초 평균. 설치된 앱은 측정 동안 껐다가 다시 켰다.
- 남은 것: 지평선 모양의 먼 땅(`far_ground_*`, 약 10만 삼각형)이 큰 창에서 혼자 약 6ms를 쓴다(먼 나무 포함 약 9ms). 이번 수정 전부터 있던 비용이다.
- 막는 법: 성능은 크롬이 아니라 앱(내장 GPU)에서 잰다. 픽셀 비율은 `pixelRatioFor` 한 곳에서만 정하고 `test/pace.test.ts`로 큰 창 예산을 확인한다. 화면 전체를 덮는 패스를 더할 때는 깊이 검사로 가려진 픽셀을 거르고, 큰 창 GPU 시간을 재서 비교한다.
